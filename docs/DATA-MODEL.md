# Recipe Data Model

**Schema:** `schemas/recipe.schema.json` (JSON Schema draft 2020-12)
**Current generation:** optional `schema_version: "2.0"`
**Status:** gradual migration; legacy recipes remain valid.

---

## 1. Source of truth

- Authored recipes: `recipes/*.yaml`.
- Canonical browser index: `recipes.json`, generated by `scripts/generate-index.js` from YAML only.
- Runtime data: fetched YAML plus `localStorage` for personal recipes and preferences.
- Never treat `recipes.json` as authored content. It is derived data.

`npm run check:index` compares the committed index against a fresh build and fails with instructions when stale. The generated output has no timestamp, so regeneration only changes the index when the YAML source changes.

---

## 2. Stable identity

- Every recipe has an `id` in the index.
- New recipes should declare `id` explicitly and it must match the filename without `.yaml`.
- Legacy recipes without `id` use the filename as the stable id and produce a migration warning.
- `scripts/validate-schema.js` rejects duplicate ids and id/filename mismatches.
- Display names may change; ids should not.
- Variations, experiments, and personal records should refer to a recipe id, not a title.

The pilot recipe uses `id: crispy-mushroom-mac-and-cheese`.

---

## 3. Required fields

```yaml
meta:
  name: string
  source: string
  base_servings: number > 0
  prep_time: string
ingredients:
  - name: string
    qty_g: number >= 0
    vol_est: string
    function: string
    ww_points: number | null
    substitutions: []
steps: [string, ...]
science_notes: [string, ...]
history: []
```

`ww_points` is deliberately nullable. `null` means **not calculated**; it does not mean zero points. Do not invent Weight Watchers values.

`substitutions` entries require `name`, a positive `ratio`, and a `science_note`. A substitution is a proposal and is not applied automatically.

---

## 4. Optional fields

The schema allows and documents:

- `schema_version`
- `id`
- `provenance` (`type`, `status`, `source_url`, `inspired_by`, notes)
- `desired_outcomes`
- `equipment` (`preferred`, `alternatives`, `experimental`)
- `testing_status` (`proposed`, `untested`, `tested`, `reviewed`)
- `variations`
- `dietary_information`
- ingredient-level `optional`, `no_scale`, `estimated`, `notes`
- additional properties at object levels

Additional properties are intentionally allowed so legacy and future metadata survive validation. That does not mean arbitrary data is displayed; it means it is not silently discarded.

The pilot recipe now carries structured provenance, desired outcomes, equipment, and testing status. Legacy recipes do not need to be migrated immediately.

---

## 5. Unknown-field preservation

Import/export must not discard data the app does not understand.

- `fetchRecipeYaml()` spreads every top-level field before normalizing known arrays.
- `loadYaml()` spreads every top-level field, preserves an explicit valid `id`, and includes science notes and history.
- `saveYaml()` exports `id` and all preserved fields.
- Ingredient-level extras are preserved by the existing spread in the import normalizer.
- ZIP and JSON backups fetch full recipes for placeholders and strip only the internal `_placeholder` flag.
- Unknown fields are preserved but are not necessarily rendered. Document any field that becomes user-visible.

---

## 6. Legacy migration rules

1. Missing `id` → filename without extension.
2. Missing `schema_version` → treated as legacy; no rewriting is performed.
3. Missing `science_notes` on import → empty array, with the user warned if the recipe is incomplete.
4. Dates: quote ISO dates in YAML (`date: "2026-11-23"`) so js-yaml does not produce a JavaScript `Date`.
5. `ww_points: null` is accepted and means not calculated.
6. Existing recipes are never automatically rewritten by validation or indexing.

Gradual migration: add `schema_version` and `id` to new recipes; backfill legacy recipes only with explicit review.

---

## 7. Local storage

| Key | Purpose |
|---|---|
| `cookbook-recipes` | Personal/working recipe array |
| `cookbook-prefs` | Unit/system preferences |
| `cookbook-deleted-recipes` | Tombstones for library recipes the user removed |

Deletion writes a tombstone so bootstrap does not resurrect a repository recipe. An explicit import of the same id clears the tombstone. Clearing site data restores the library.

No storage schema version exists yet. Add one before changing stored shapes; migrations must be explicit and tested.

---

## 8. Recipe variations and experiments

The schema allows optional `variations` and `testing_status`. The pilot recipe records:

- `provenance.type: adaptation`
- `provenance.status: proposed`
- `testing_status: untested`
- desired outcomes and equipment alternatives

A kitchen experiment template is kept in `docs/crispy-mushroom-mac-and-cheese-testing.md`. It uses blank observations and `null` values; it is not populated with invented results. A dedicated personal-experiment store/export is a Milestone 2 deliverable, not implemented yet.

---

## 9. Validation and tests

```bash
npm run validate:schema   # JSON Schema + stable IDs + duplicates
npm run validate:recipes  # project-specific recipe quality rules
npm run check:index       # generated index is synchronized
npm run test:unit         # fixtures for scaling, units, import/export, nutrition, deep links
```

Fixture expectations live in `tests/` and describe the input, expected result, and limitations. A green test does not prove an untested cooking claim or complete nutritional coverage.
